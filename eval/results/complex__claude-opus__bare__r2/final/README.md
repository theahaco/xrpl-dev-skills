# mpt-issuer

Issuer-side compliance controls for a regulated, stablecoin-style Multi-Purpose Token (MPT) on the XRP Ledger.

```ts
import { Client, Wallet } from 'xrpl'
import { JsonFileBanRegistry, MptIssuer } from './src/index.js'

const client = new Client('wss://s.altnet.rippletest.net:51233')
await client.connect()
const issuer = await MptIssuer.connect(client, Wallet.fromSeed(process.env.ISSUER_SEED!), issuanceId, {
  banRegistry: new JsonFileBanRegistry('state/ban-registry.json'), // use a DB-backed BanRegistry in production
})

await issuer.authorizeHolder(addr)          // allowlist (after KYC; holder must opt in first)
await issuer.issue(addr, '250.00')
await issuer.clawback(addr, '100')
await issuer.freezeHolder(addr); await issuer.unfreezeHolder(addr)
await issuer.freezeAll();        await issuer.unfreezeAll()
await issuer.banHolder(addr, 'sanctions match')
```

Amounts are decimal strings at the issuance's `AssetScale`. Anything that can't be represented exactly is rejected, never rounded. Each state-changing call waits for a validated ledger and throws an `IssuerError` (with a `code`) unless it succeeded. Calls that find the ledger already in the requested state return `{ txHash: null }`.

## How each control is enforced

| Control | Ledger mechanism | Enforced by the module |
|---|---|---|
| Allowlist | `tfMPTRequireAuth`; issuer `MPTokenAuthorize` per holder | refuses to approve or pay banned addresses |
| Clawback | `tfMPTCanClawback`; `Clawback` | refuses to claw back more than the balance (the ledger would silently take less) |
| Per-holder freeze | `tfMPTCanLock`; `MPTokenIssuanceSet` + `Holder` | `issue()` refuses frozen holders |
| Global freeze | `MPTokenIssuanceSet` without `Holder` | `issue()` refuses while frozen |
| Ban | removed from allowlist → full clawback → frozen | durable `BanRegistry` blocks re-approval; state is re-verified after the ban |

`createIssuance` never enables escrow, DEX trading or confidential balances. Each of those would let tokens sit outside a holder's balance, where clawback and bans might not reach them. `connect` refuses any issuance that has them enabled, is missing a required control, or has a `DomainID` (which would admit holders who aren't on the allowlist).

### Protocol behaviour to be aware of (verified on testnet)

- **Freezes only stop transfers between holders.** The ledger still lets the issuer pay a frozen holder, or pay anyone during a global freeze. `issue()` blocks this, so all issuance must go through the module.
- **A frozen holder can still send tokens back to the issuer.** The protocol always allows this (as with trust-line freezes). The tokens go into issuer custody. Your off-ledger redemption process must not pay out to frozen holders.
- Banned holders cannot send to anyone, including the issuer (`tecNO_AUTH`). If a banned holder deletes and re-creates their MPToken entry, it comes back unapproved.
- Clawback and bans work during a global freeze.

### Operational notes

- The ledger has no native "ban" state, so the `BanRegistry` is the source of truth. Back it with the same durable, audited store used for KYC decisions.
- Transactions are serialised per `MptIssuer` instance. Run only one instance per issuer account.
- Transaction hashes are logged before submission, so an interrupted process can be reconciled.
- For production, sign with a regular key or multisig rather than the master key, and load it from a secrets manager.

## Demo

```sh
cp .env.example .env    # fill in ISSUER_ADDRESS / ISSUER_SEED
npm install
npm run demo            # uses ISSUER_SEED and writes result.json
npm run demo -- --scratch   # dry run with a faucet-funded issuer
```

Holder seeds generated by the demo are saved to `.secrets/` (gitignored), and the ban registry is saved to `state/`.
